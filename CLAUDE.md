# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Qt 6 / QML Home Assistant dashboard (`qthomeassistant`) that talks to HA over its WebSocket API. Targets desktop (macOS) and Android (fullscreen when `platform == "android"`).

## Build, run, lint

Requires Qt ≥ 6.7 and < 6.12 (Gui, Quick, QuickControls2, Multimedia, WebSockets, Network, Widgets, Charts; Mqtt optional), Python 3 (used at configure time), CMake, Ninja. The floor is 6.7, not something newer, specifically so Android builds can target Qt 6.7.x — see Android below for why. The ceiling (`find_package(Qt6 6.7...<6.12)`) is because Qt Charts, used by the energy detail overlays, is deprecated since 6.10 and may be dropped in 6.12; Charts' QML types also need a `QApplication`, which is why `main.cpp` uses one instead of `QGuiApplication` (and why Widgets is linked). `Mqtt` is optional: configure only warns if it's missing, and the app then builds without `MqttPublisher` (`QTHASS_HAS_MQTT` undefined, `RemoteAdmin`'s `listSettings` reports `mqttEnabled: false`). It has no prebuilt aqt package for this project's kits, so to get MQTT publishing build it from source first — see "Qt MQTT (built from source)" below.

```sh
cmake --preset desktop
cmake --build --preset desktop
cmake --build --preset desktop --target all_qmllint   # qmllint over the QML module
```

`CMakePresets.json` (committed) only defines hidden base presets (generator, `build/${presetName}` layout, common cache variables) -- it has no Qt paths, since those are machine-specific. `CMakeUserPresets.json` (gitignored) supplies the three concrete, buildable presets: `desktop`, `qt67`, and `qt610` (`cmake --list-presets` to see them; see Android below for the latter two). `desktop` overrides its `binaryDir` to `build/debug` specifically, since that's what `compile_commands.json` symlinks to. If `CMakeUserPresets.json` is ever missing, recreate `desktop` with `CMAKE_PREFIX_PATH` pointed at a Qt ≥ 6.7 macOS kit (`$HOME/Qt/6.10.1/macos` on this machine); if the Qt version matters, check `Qt6_DIR` in `CMakeCache.txt`.

Run (macOS bundle). The app's runtime config -- `HASS_URL` (e.g. `wss://host/api/websocket`; `ws://` for plain HTTP), `HASS_TOKEN` (long-lived access token), and the optional `DASHBOARD_URL`/`IDLE_TIMEOUT_SECONDS`/`REMOTE_ADMIN_PASSWORD`/`REMOTE_ADMIN_PORT`/`MQTT_BROKER_HOST`/`MQTT_BROKER_PORT`/`MQTT_USERNAME`/`MQTT_PASSWORD` keys -- is baked into the binary at configure time from `.envrc` (`export KEY="value"`) and/or a repo-root `config` file (`KEY=VALUE`, no `export`, no quotes; wins over `.envrc` for a key set in both). See `Controler` below. So a plain launch works; `HASS_URL`/`HASS_TOKEN` environment variables, when set, override the bundled values, and values saved from the in-app settings page override both:

```sh
build/debug/qthomeassistant.app/Contents/MacOS/qthomeassistant
```

Both hold the real HA token and are kept out of git only by ignore rules outside the repo (there's no `.gitignore`): `.envrc` by a global ignore, `config` by a repo-local `.git/info/exclude` entry, which has to be added per clone since its generic name isn't covered globally.

Verbose logs: `QT_LOGGING_RULES="qthass.*.debug=true"` (categories `qthass.api`, `qthass.controller`).

There are no tests.

### Qt MQTT (built from source)

`Mqtt` (optional; needed only for `MqttPublisher`, see Architecture below) has no prebuilt aqt package for any Qt version/platform combination this project uses, so it's built from source, once per kit, straight into that kit's own install prefix -- `qt-cmake` from a binary Qt kit already points `CMAKE_INSTALL_PREFIX` at that kit's prefix, so `cmake --install` drops `Qt6Mqtt` in next to the other Qt6 modules and `find_package(Qt6 ... COMPONENTS Mqtt)` just starts working, no `CMAKE_PREFIX_PATH` changes needed anywhere. Already done for all three kits this project builds (`~/Qt/6.10.1/macos`, `~/Qt/6.7.3/android_arm64_v8a`, `~/Qt/6.10.1/android_arm64_v8a`) -- only needed again if a kit is reinstalled from scratch.

Two things needed overriding on this machine, both required regardless of which kit is being built:

- **No full Xcode, only Command Line Tools.** Building an *application against* Qt (this project's own `qt_add_executable`) never needs Xcode.app, but building a *Qt module itself from source* goes through `qt_build_repo`, which unconditionally shells out to `xcodebuild -version` to sanity-check the Xcode/SDK version pairing -- and fails configure outright (`Can't determine Xcode version`) when only the Command Line Tools are installed. `-DQT_NO_APPLE_SDK_AND_XCODE_CHECK=ON` skips that check entirely; plain CLI compilation doesn't otherwise need Xcode.app.
- **Ninja Multi-Config's AUTOMOC "better graph" mode is broken here.** `qt-cmake`'s default generator (Ninja Multi-Config) hits a real bug in CMake's per-config AUTOMOC dependency tracking for Qt ≥ 6.8 modules (`AUTOGEN_BETTER_GRAPH_MULTI_CONFIG`, on by default for Qt 6.8+): the build graph ends up depending on a `<Module>_fake_header.h` that no rule ever generates (`ninja: error: '.../Mqtt_fake_header.h', needed by '.../Mqtt_autogen_timestamp_deps-Debug', missing and no known rule to make it`). Neither downgrading CMake below the 3.29 version that introduced the feature nor disabling the `CMAKE_AUTOGEN_BETTER_GRAPH_MULTI_CONFIG` cache variable avoids it (Qt's own `qt_internal_add_module` sets the *target* property directly once it detects Qt ≥ 6.8, overriding the cache variable's default). The fix that actually works: don't use a multi-config generator at all -- pass `-G Ninja -DCMAKE_BUILD_TYPE=Release` instead of accepting `qt-cmake`'s default, which sidesteps the whole per-config autogen graph this bug lives in.

Recipe, parameterized per kit (`<qt_version>` matches the target kit exactly -- `6.10.1` for desktop/`qt610`, `6.7.3` for `qt67`; `<kit_bin>` is that kit's own `bin/qt-cmake`; Android kits additionally need `-DQT_HOST_PATH=<host_qt>/bin/qt-cmake`'s macOS host counterpart, e.g. `~/Qt/6.7.3/macos` for `qt67`, already the same path used as `QT_HOST_PATH` in `CMakeUserPresets.json` for the app's own Android presets):

```sh
git clone --branch v<qt_version> --depth 1 https://github.com/qt/qtmqtt.git /tmp/qtmqtt-<kit>
<kit_bin>/qt-cmake -G Ninja -S /tmp/qtmqtt-<kit> -B /tmp/qtmqtt-<kit>-build \
  -DQT_NO_APPLE_SDK_AND_XCODE_CHECK=ON -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/qtmqtt-<kit>-build
cmake --install /tmp/qtmqtt-<kit>-build
rm -rf /tmp/qtmqtt-<kit> /tmp/qtmqtt-<kit>-build
```

Verify a given kit has it with `ls <kit_prefix>/lib/cmake/Qt6Mqtt`.

### Android

The build targets Qt **6.7.3**, not the newer 6.10.1 used for desktop: Qt 6.8+ raised Android's floor to API 28 and `libQt6Core` started calling `getentropy()` (added to Bionic libc only in API 28), so anything built with Qt ≥ 6.8 hard-crashes with `UnsatisfiedLinkError: dlopen failed: cannot locate symbol "getentropy"` on any API 27-or-older device — confirmed on a real device (Android 8.1 / API 27) in 2026-09. Qt 6.7.3's `libQt6Core` doesn't reference that symbol, and its default `qtMinSdkVersion` is 23 (Android 6.0), so the same source now installs and runs down to API 27+ without any minSdk override — lowering `QT_ANDROID_MIN_SDK_VERSION` on a Qt ≥ 6.8 build does *not* work (the manifest check passes but it still crashes at library load), it has to be a different Qt version. If a device this old ever stops mattering, upgrading back to 6.10.1 (already installed at `~/Qt/6.10.1`) is a drop-in swap of the paths below.

On this machine: Android Studio + `android-commandlinetools` (Homebrew casks) provide the SDK, rooted at `/opt/homebrew/share/android-commandlinetools`; NDK r26b (`ndk;26.1.10909125`) matches what the `~/Qt/6.7.3/android_arm64_v8a` kit was built against (check `qt.toolchain.cmake`'s `__qt_initially_configured_toolchain_file` if that ever changes — the 6.10.1 kit instead wants NDK r27c, `ndk;27.3.13750724`); JDK 17 (`temurin@17`) is required for Gradle — the system default JDK can stay newer, just override `JAVA_HOME` for the build.

Qt 6.7.3's Gradle templates pull AGP 7.4.1, whose bundled `aapt2` can't parse the `android-36` platform jar (androiddeployqt's default compileSdk is always "the highest installed platform," and this machine's SDK has `android-36` installed for the 6.10.1 kit) — it fails resource linking with `aapt2 E ... RES_TABLE_TYPE_TYPE entry offsets overlap actual entry data`. Qt 6.7.3 has no CMake-level `QT_ANDROID_COMPILE_SDK_VERSION` property to override this (that property only exists from Qt 6.8+), so the fix is a second, isolated `ANDROID_SDK_ROOT` at `~/Android/sdk-compat-api34` — symlinks to the real SDK's `platform-tools`, `cmdline-tools`, `licenses`, `emulator`, `build-tools/35.0.0`, and `ndk/26.1.10909125`, but only `platforms/android-34` (not `android-36`), so androiddeployqt's "highest installed" scan lands on 34, which AGP 7.4.1 can parse and which still covers Qt 6.7.3's `qtTargetSdkVersion` (also 34). `cmake/android.cmake` pins `QT_ANDROID_COMPILE_SDK_VERSION` to `android-34` whenever `Qt6_VERSION VERSION_LESS 6.8`, for the same reason. Recreate the symlink farm if `~/Android/sdk-compat-api34` is ever missing:

```sh
ISO=$HOME/Android/sdk-compat-api34
mkdir -p "$ISO/platforms" "$ISO/build-tools" "$ISO/ndk"
ln -sfn /opt/homebrew/share/android-commandlinetools/{platform-tools,cmdline-tools,licenses,emulator} "$ISO/"
ln -sfn /opt/homebrew/share/android-commandlinetools/build-tools/35.0.0 "$ISO/build-tools/35.0.0"
ln -sfn /opt/homebrew/share/android-commandlinetools/ndk/26.1.10909125 "$ISO/ndk/26.1.10909125"
ln -sfn /opt/homebrew/share/android-commandlinetools/platforms/android-34 "$ISO/platforms/android-34"
```

Build with the `qt67` preset (`qt610` for the API 28+ kit -- same commands, just swap the preset name; it doesn't need the isolated SDK root, so it points `ANDROID_SDK_ROOT` straight at `/opt/homebrew/share/android-commandlinetools`):

```sh
cmake --preset qt67
cmake --build --preset qt67 --target apk
cmake --build --preset qt67 --target run   # install + launch on whatever device adb targets
```

The `qt67`/`qt610` presets in `CMakeUserPresets.json` set `toolchainFile`, `QT_HOST_PATH`, `CMAKE_PREFIX_PATH`, `ANDROID_SDK_ROOT`, `ANDROID_NDK_ROOT` (as both `environment` and `cacheVariables`, since `cmake/android.cmake`'s `run` target reads it from the environment while CMake's own Android tooling reads the cache variable) and `JAVA_HOME` (environment only) for their respective kit; `binaryDir` is pinned to `build/android-arm64-qt67` / `build/android-arm64` rather than the presets' default `build/${presetName}`, to match the paths used below and elsewhere in this doc.

`run` (in `cmake/android.cmake`, `ANDROID`-only) depends on `qthomeassistant_make_apk`, so it builds first if needed; it shells out to `adb`, located via `ANDROID_SDK_ROOT/platform-tools` or `PATH`, to install and launch. The APK it installs is the stable `android-build/qthomeassistant.apk` androiddeployqt copies its final output to (`${apk_final_dir}/${target}.apk`, not the deeper `android-build/build/outputs/apk/debug/android-build-debug.apk` gradle path, which is more of an implementation detail). Nothing else is pushed to the device: the dashboard QML and the HASS config are both inside the APK. It hardcodes the package name once, in the `ANDROID_PACKAGE_NAME` CMake variable (`org.qtproject.example.qthomeassistant`, androiddeployqt's default since nothing sets `QT_ANDROID_PACKAGE_NAME`) — update it there if that's ever set explicitly.

The AVD (`qthass`, Pixel 6 profile, `system-images;android-34;google_apis;arm64-v8a`) was created with `avdmanager create avd`; `avdmanager list avd`'s `devices.xml` lookup errors on this SDK layout but the AVD still gets created fine. Launch with `emulator -avd qthass`, then `cmake --build --preset qt67 --target run` (it's API 34, so `qt610` works too), or by hand:

```sh
adb install -r build/android-arm64-qt67/android-build/qthomeassistant.apk
adb shell am start -n org.qtproject.example.qthomeassistant/org.qtproject.qt.android.bindings.QtActivity
adb logcat -s libqthomeassistant_arm64-v8a.so qthass.api:D qthass.controller:D
```

Since the config is bundled, the token ends up inside the APK — fine for a personal debug build, don't distribute it.

## Architecture

### QML loading

- The app itself -- shell (setup wizard, settings, screensaver, system tray) and every built-in card -- is compiled into the `QtHomeAssistant` QML module and embedded under `qrc:/res/QtHomeAssistant/qml/...`. Every new QML/JS file must be added to `QML_FILES` in `CMakeLists.txt`, and changes need a rebuild. Subdirectory files (`qml/Cards/`, `qml/Features/`, `qml/Dashboard/`) are still registered by basename, so `import QtHomeAssistant` is enough to use them.
- The dashboard is not part of the app: it's user-written QML from one configured URL (`Controler.dashboardUrl`), downloaded into a local cache and loaded from there (see "User dashboards"). That's the settled way to customize the app without a rebuild -- a single URL plus a cache, not a filesystem search path; don't add one.
- `qml/Dashboard/DashboardHost.qml` in `Main.qml` holds the dashboard, which exists only while `HassAPI.connected` (and setup is done), so no entity components exist until auth succeeds. It is torn down again on disconnect.

### C++ singletons exposed to QML (`QML_SINGLETON`, registered via `qt_add_qml_module` SOURCES)

- **`HassAPI`** (`hassapi.{h,cpp}`) owns the `QWebSocket`. Flow: `connect()` → `auth_required` → send token → `auth_ok` sets `connected`. Incoming messages are dispatched by `type` through `message_handlers_`.
  - **Reconnect:** once `connect()` has been called, the connection is kept up: any disconnect or failed attempt (HA restarting, host unreachable, `auth_invalid`) retries every 5 s (flat, like `MqttPublisher`), re-reading URL/token from `Controler` each time. An attempt not authenticated within 20 s is aborted (a TCP connect to a down host can otherwise hang for over a minute), and while connected HA's `ping`/`pong` runs every 30 s -- a ping still unanswered at the next one drops the connection, catching dead sockets no close frame ever arrives for. On disconnect the dashboard `Loader` tears down and every card unregisters its callback, so `auth_ok` starts from a clean slate and the rebuilt dashboard re-subscribes; verified against a fake HA server (clean close, connection refused, frozen server).
  - `registerStateChanges(entity_id, jsFunction)` stores the callback and sends a per-entity `subscribe_entities`. It deliberately avoids `get_states`: that payload is several MB and trips QWebSocket's incomplete-frame timeout (close code 1001). Registrations made before connect are subscribed on `auth_ok`. Late registrations for an already-subscribed entity get the cached state replayed.
  - Events use HA's compressed format (`a` added / `c` `+`/`-` diff / `r` removed), rebuilt into full per-entity state in `entity_states_`.
  - **Callback contract:** callbacks receive a JSON *string* of `{entity_id, state, attributes, last_changed}` (`last_changed` in seconds since the epoch), so QML must `JSON.parse` it. There is no `type: "event"` wrapper, so the `j['type'] === 'event'` branch in `Light.qml` never runs.
  - `command(type, params, owner, fn)` sends any other one-off WebSocket command (e.g. `recorder/statistics_during_period`) and calls `fn(ok, resultJson, errorMessage)` with the reply's `result` (any JSON value, e.g. the plain string `auth/long_lived_access_token` returns); the reply is dropped if `owner` (pass the calling QML object) is destroyed or the connection drops first.
  - `subscribe(type, params, owner, fn)` is the same for subscription commands (`persistent_notification/subscribe`, `subscribe_events`, `render_template`, ...): `fn(ok, eventJson, errorMessage)` gets each event's `event` (or `ok` false once, when HA refuses, e.g. an admin-only command for a non-admin), routed by id ahead of the `subscribe_entities` handling. It returns the id for `unsubscribe(id)` (sends `unsubscribe_events`, which ends any subscription), ends by itself once `owner` is gone, and like every subscription doesn't survive a reconnect -- subscribe again when `connected` comes back.
  - `authenticationFailed(message)` is emitted on `auth_invalid` (retries continue regardless); the setup wizard uses it to report a rejected login.
  - Service calls are hand-written slots. `light(entity_id, on)` is currently the only one; new domains should follow its `call_service` pattern.
- **`Controler`** (`controller.{h,cpp}`; note the single-`l` spelling, which QML uses too) provides a `screensaverActive` bool property backed by an idle timer (single-shot; any interaction restarts it), an `idleTimeoutSeconds` int property, a `hassConnected` bool property, and an `error(QString)` signal. `hassConnected` exists purely so `RemoteAdmin` (C++) can read `HassAPI.connected` (QML) — `HassAPI::create()` isn't cached the way `Controler::create()` is (a cached-pointer version was tried and abandoned: QML was observed constructing a second, separate `HassAPI` instance that ended up being the one actually driving the real connection, leaving a C++-side cached pointer referencing an orphaned object with stale state), so `Main.qml`'s `Connections { target: HassAPI; function onConnectedChanged() { Controler.hassConnected = HassAPI.connected } }` mirrors it across instead, since QML's own property bindings on `HassAPI` are reliably consistent even though a stable C++ pointer to it isn't. `keepScreenOn` (saved in `QSettings` as `display/keepScreenOn`, off by default, toggled from the settings page's Idle section) sets or clears `FLAG_KEEP_SCREEN_ON` on the Android activity window via JNI on the Android UI thread -- the same flag as the HA companion app's "Keep screen on"; `keepScreenOnSupported` is false off Android, where the switch is disabled. `batteryLevel` (percent, -1 while unknown) and `batteryCharging` are polled every 15 s on Android only (`batterySupported`), from the sticky `ACTION_BATTERY_CHANGED` broadcast (`registerReceiver(null, ...)`, no permission or Java code needed; preferred over `BatteryManager.getIntProperty()`, which returns garbage on some older devices); charging counts being plugged in at all, so a tablet held at a charge limit still shows the bolt. `qml/SystemTray/SystemTray.qml` -- a status-bar-style pill of indicators in the top right corner of `Main.qml` and, dimmed, of `Screensaver.qml` (which moves its clock below it), hidden while none is shown; each indicator is behind its own `show...` property, and the pill decides visibility from those booleans rather than the indicators' `visible`, which reads false while the pill itself is hidden -- shows them through `BatteryIndicator.qml` when `UiSettings.showBattery` is on (off by default, the settings page's System tray section, disabled off Android). The same pill shows, on any platform and only while above zero, Home Assistant's notification count (`showNotifications`, a bell) and its Settings badge, repairs plus updates (`showSettingsAlerts`, a cog), both off by default. They come from `qml/SystemTray/HassAlerts.qml`, one instance in `Main.qml` passed to both trays so there's one set of subscriptions, counted the way HA's own sidebar (`ha-sidebar.ts`) does: `persistent_notification/subscribe`, kept as a by-id map since `added`/`updated` events carry only the delta; `repairs/list_issues` issues not `ignored`, refetched 500 ms after a `repairs_issue_registry_updated` event; and a `render_template` subscription counting `update.*` entities that are on, not `is_hidden_entity` and support INSTALL (odd `supported_features`). Repairs and `render_template` are admin-only; for a non-admin that count stays 0. `HassAlerts` keeps the lists as well as the counts: on the main screen (`SystemTray.expandable`, off on the screensaver, where a tap dismisses it) tapping the pill expands it into `SystemTrayPanel.qml`, a popup that opens exactly over the pill (its rect mapped into the overlay with `mapToItem` on each open: on Android the window content sits below a top inset the overlay covers) and grows down and left from its top right corner as `progress` animates 0 → 1: the counts fade out, the battery stays put (the pill's row is `SystemTrayIndicators.qml`, shared so both line up), the background blends from the pill's into the dialog color, and the details, laid out at the final size and revealed by clipping rather than reflowed per frame, fade in. Closing (tap outside, or on the pill's spot) runs it back into the pill, which is hidden while the panel is open. The panel lists each notification (title, Markdown message, age; Markdown images are pulled out of the text into `Image`s scaled down to the panel's width, since a `Label` draws them at their own size -- the vacuum's notifications embed an 828 px PNG as a `data:` URL), repair issue (title and description from `frontend/get_translations` for the user's `frontend/get_user_data` language, `{placeholders}` filled from `translation_placeholders`; domain, severity, Learn more) and update (installed → latest; the template renders them as a JSON array string). Relative links open on the HA server (`Controler.hassUrl`, `ws` → `http`). The panel draws its own plain background rather than Material's elevated one, which doesn't render under the software renderer. Markdown links stay Qt's default blue: neither `linkColor` nor `palette.link` reaches them. Checked against the real server, including a notification added and dismissed while running. `screensaverActive` and `idleTimeoutSeconds` are the single source of truth for `qml/Screensaver.qml` (bound directly to `screensaverActive`; a clock, `WeatherSummary` (condition, temperature, today's high/low) and `EnergySummary` (solar now and today vs the Solcast forecast, home now and today, battery, grid) in dim colors on black; the clock and weather move together to a new random position every minute against burn-in, in the room above the energy summary, which stays centered along the bottom edge; the summaries exist only while it's shown and connected, and read the entities `Main.qml` passes as `weatherEntity`/`energyEntities` from the loaded dashboard's `screensaverWeatherEntity`/`screensaverEnergyEntities`, each shown only when set -- in the office panel's `main.qml`, the same sensors as `OfficeEnergy.qml`, kept in sync by hand), the settings page, *and* `RemoteAdmin` (see below) — all just call `Controler::setScreensaverActive()`/`setIdleTimeoutSeconds()` rather than each keeping their own state. `main.cpp` installs `Controler` as an event filter on the root window; any touch/key/mouse press calls `setScreensaverActive(false)`, which rearms the idle timer. `main.cpp` fetches the `Controler`/`RemoteAdmin` pointer via `engine.singletonInstance<Controler *>("QtHomeAssistant", "Controler")`, called *before* `engine.load()` -- calling `Controler::create()`/`instance()` directly from C++ *after* `load()` was observed to race QML's own singleton resolution and return a second, disconnected instance (each internally self-consistent, silently wrong); `singletonInstance()` goes through the engine's own registry instead, guaranteeing it's the exact instance QML will use, and calling it before `load()` makes it unambiguously the first resolution. The engine builds that instance with the constructor, not `Controler::create()`, so the constructor makes the first instance `s_instance`: before that, `HassAPI` (which reaches `Controler` through `create()`) got a second instance that never saw values set from QML -- a URL/token saved from the settings page or the setup wizard only took effect after a restart, and the wizard's first test run connected with the stale bundled credentials instead.

  Config: on construction `Controler` reads the bundled `:/qt-hass/config` resource (`KEY=VALUE`). `REMOTE_ADMIN_PASSWORD`/`REMOTE_ADMIN_PORT` are defaults for the `remoteAdminEnabled`/`remoteAdminPassword`/`remoteAdminPort` properties (enabled by default exactly when the bundle has a password), overridden by values saved at setup (`setRemoteAdminConfig()`, `QSettings` `remoteAdmin/*`); `remoteAdminConfigChanged()` makes `RemoteAdmin` close and listen again. `deviceName` (writable, `QSettings` `device/name`, falls back to `hostName()`) is the name set at setup; `setupCompleted` (`setup/completed`) gates the setup wizard, see below; until it's first saved it defaults to whether a token was configured at startup, so existing installs (e.g. a bundled token) don't get the wizard. `MQTT_*` are defaults for the `mqttBrokerHost`/`mqttBrokerPort`/`mqttUsername`/`mqttPassword` properties, overridden by values saved from the settings page's MQTT section (`setMqttConfig()`, persisted in `QSettings` under `mqtt/*`; `clearSavedMqttConfig()` is its "Use built-in"). `mqttConfigChanged()` makes `MqttPublisher` reconnect; `mqttSupported` (constant, whether `QTHASS_HAS_MQTT` is defined) greys that section out in builds without Qt MQTT, and `mqttConnected` is set by `MqttPublisher` for its status label. `HASS_URL`/`HASS_TOKEN` resolve in increasing priority from the bundle, the `HASS_URL`/`HASS_TOKEN` environment variables, then values saved from the settings page (writable `hassUrl`/`hassToken` properties, persisted in `QSettings`); `HassAPI` reads them from `Controler` only, `clearSavedConnection()` drops the saved ones again (the settings page's "Use built-in" button), and `HassAPI.reconnect()` aborts the socket and reconnects with the current values. `idleTimeoutSeconds` defaults to the bundled `IDLE_TIMEOUT_SECONDS` (else 60) and changes from the settings page or `RemoteAdmin`'s `setStringSetting` persist in `QSettings`. The resource is generated at configure time by `tools/generate_config.py` from `.envrc` and/or the repo-root `config` file into `build/*/generated/config` — the build dir only, never the source tree, since it holds the real token and passwords; only the keys above are copied, so unrelated `.envrc` exports stay out of the binary. Both inputs are configure dependencies, so editing either and rebuilding picks up the change; neither existing only warns and bundles an empty config. Once a URL/token or idle timeout has been saved from the app, edits to `.envrc`/`config` for those keys no longer take effect on that machine until the saved values are cleared (`connection/url`, `connection/token`, `idleTimeout` in the `qt-hass`/`qthomeassistant` QSettings store, named in `main.cpp`). Deliberately simple until there's a real story for how others customize a build; don't reintroduce a writable config file search without settling that first.
- **`RemoteAdmin`** (`remoteadmin.{h,cpp}`) is a minimal Fully-Kiosk-Browser-style remote admin server: `GET http://<device>:<REMOTE_ADMIN_PORT>/?cmd=<command>&password=<REMOTE_ADMIN_PASSWORD>[&key=...&value=...]`, JSON responses (`{"status":"OK"|"Error", ...}`). Hand-rolled on `QTcpServer`/`QTcpSocket` rather than `Qt6::HttpServer` — the wire protocol is GET-only with no body, and this avoids a Qt module that isn't guaranteed installed for the pinned Qt 6.7.3 Android kit. Mirrors real Fully Kiosk's wire *conventions* (query-string `cmd`/`password`, JSON envelope, familiar command names) for the commands this app actually supports. `deviceInfo` includes `deviceID`/`deviceName`/`Mac`/`ip4`/`deviceManufacturer`/`deviceModel`/`appVersionName` purely so Home Assistant's official `fully_kiosk` integration works at all -- confirmed field-by-field via HA's own logs, since each missing one throws a bare, uncaught `KeyError` (no `.get()`/default anywhere in these code paths): `config_flow.py`'s `_create_entry` needs `deviceID`/`deviceName`/`Mac` just for "Add device" to succeed (HA's UI shows any failure there as "Unknown error occurred"), and separately `entity.py`'s `FullyKioskEntity.__init__` -- the base class almost every entity platform (switch, camera, media_player, notify, image, button) constructs -- additionally needs `ip4`, `deviceManufacturer`, `deviceModel`, `appVersionName`, or that whole platform creates zero entities. `deviceManufacturer` is hardcoded to `"qthomeassistant"` (this is not real hardware), `deviceModel` is `QSysInfo::prettyProductName()`, `appVersionName` is `APP_VERSION` (a compile definition set from `CMakeLists.txt`'s `PROJECT_VERSION`). `isInScreensaver` mirrors `screensaverActive` under Fully Kiosk's own field name -- `switch.py`'s "screensaver" `FullySwitchEntityDescription` reads its on/off state via `is_on_fn=lambda data: data.get("isInScreensaver")`, so without this exact key that switch always reported "off" regardless of what `startScreensaver`/`stopScreensaver` actually did. This is still **not** a real drop-in: `sensor.py`/`binary_sensor.py` are better-behaved (`coordinator.data.get(...)` plus an `if description.key in coordinator.data` existence check, so they degrade gracefully instead of crashing) but want battery, RAM, storage, foreground app, screen orientation, etc. -- this app has no equivalent for any of that, so those entities stay absent rather than being faked. `switch.py`'s other four switches (`maintenance`/`kiosk`/`motion-detection`/`screenOn`, reading `maintenanceMode`/`kioskLocked`/`settings.motionDetection`/`screenOn`) are in the same boat *and* call commands (`enableLockedMode`, `lockKiosk`, `enableMotionDetection`, `screenOn`) this server doesn't implement at all -- they'll show "off" and fail with "Unknown command" if toggled. Point HA's generic `rest`/`rest_command`/`switch` platforms at this server instead if you want reliable behavior. Only listens while `Controler::remoteAdminEnabled()` with a non-empty `remoteAdminPassword()` (bundled `REMOTE_ADMIN_PASSWORD`, or set at setup; see `Controler` above) — no unauthenticated control surface by default. Plaintext HTTP, password in the URL query string (same weak model as real Fully Kiosk) — LAN-only, never port-forward this. Default port 2323 (`REMOTE_ADMIN_PORT` to override). Commands: `deviceInfo` (returns `deviceID`/`deviceName`/`Mac`/`ip4`/`screensaverActive`/`isInScreensaver`/`idleTimeoutSeconds`/`hassConnected`), `startScreensaver`/`stopScreensaver`, `getStringSetting`/`setStringSetting&key=idleTimeoutSeconds&value=<seconds>` (`idleTimeoutSeconds` is this app's own setting key; `timeToScreensaverV2`, Fully Kiosk's real one, is accepted as a synonym -- HA's `number.py` only creates its "screensaver timer" entity when that key is in `listSettings`, and sets it through `setStringSetting` with that key. `0` disables the screensaver, as in Fully Kiosk), `getScreenshot` (a PNG of the app window, `Content-Type: image/png`, via the grab function `main.cpp` passes to `RemoteAdmin::setScreenshotSource()` -- python-fullykiosk returns the raw body only for an `image/*` content type and parses JSON otherwise; HA's `image.py` creates the screenshot entity unconditionally), `listSettings` (HA's `fully_kiosk` coordinator polls this — via `python-fullykiosk`'s `getSettings()`, a *different* wire command from `getStringSetting`/`setStringSetting` above — on every refresh alongside `deviceInfo`; returns `{"idleTimeoutSeconds": ..., "timeToScreensaverV2": ..., "mqttEnabled": ...}`, plus `mqttEventTopic` when `mqttEnabled` is true, with no `status` wrapper, since the coordinator merges it as-is under `deviceInfo`'s `settings` key — a missing `mqttEnabled` key would leave the screensaver/screen switches permanently "unavailable", since `entity.py`'s `mqtt_subscribe()` does `data["settings"]["mqttEnabled"]` with no default and the exception happens after the entity's already added, so it never gets a first coordinator update). `mqttEnabled` mirrors whether `MqttPublisher` (below) is configured (`!Controler::mqttBrokerHost().isEmpty()`), not a live connection check. HA's `fully_kiosk` integration otherwise only polls this server on a fixed 30 s interval (`homeassistant/components/fully_kiosk/const.py`'s `UPDATE_INTERVAL`, not configurable from our side), so without MQTT a local screensaver dismiss can take up to 30 s to show up in HA's switch state; see `MqttPublisher` below for how that lag is avoided when MQTT is configured.
- **`MqttPublisher`** (`mqttpublisher.{h,cpp}`) is a plain `QObject` (like `RemoteAdmin`, no QML surface) that publishes this device's screensaver state to an MQTT broker in exactly the shape HA's `fully_kiosk` integration expects for its push path, so `switch.py`'s screensaver switch updates immediately instead of waiting for the 30 s poll mentioned above. Confirmed by reading `entity.py`'s `mqtt_subscribe()`: it only subscribes if `data["settings"]["mqttEnabled"]` is truthy, and builds the topic from `data["settings"]["mqttEventTopic"]` by replacing `$appId`→`"fully"`, `$event`→the event name, `$deviceId`→`deviceInfo`'s `deviceID`; `switch.py`'s screensaver entry uses `mqtt_on_event="onScreensaverStart"`/`mqtt_off_event="onScreensaverStop"`, and the payload just needs to be JSON containing `{"event": "<name>"}` (extra fields are ignored). `kMqttEventTopicTemplate` (`controller.h`) is the literal template string (`"$appId/event/$event/$deviceId"`) shared between `RemoteAdmin::cmdListSettings()` (which advertises it) and `MqttPublisher` (which resolves it the same way before publishing) — a single source of truth so the two can't drift apart. `Controler::deviceId()` (hoisted out of what used to be `RemoteAdmin::deviceMac()`) is the shared MAC-based id used for both `deviceInfo`'s `deviceID` and the topic's `$deviceId`. `Controler::deviceName()`/`deviceIp()` (hoisted out of `RemoteAdmin` the same way) back `deviceInfo`'s `deviceName`/`ip4` and, via `Controler.systemInfo()`, the settings page's About section (name, all IPv4 addresses, MAC, remote admin port, app/OS/Qt versions), which refreshes each time the settings open. Only compiled in when Qt MQTT is found at configure time (`QTHASS_HAS_MQTT`; otherwise `main.cpp` just warns if `MQTT_BROKER_HOST` is set). Only connects if `MQTT_BROKER_HOST` is set in the bundled config (see `Controler` above) — same empty-means-disabled gating as `REMOTE_ADMIN_PASSWORD`; `MQTT_BROKER_PORT` defaults to 1883, `MQTT_USERNAME`/`MQTT_PASSWORD` are optional (anonymous if unset). Plain TCP, no TLS support yet — LAN-only broker assumed, consistent with this file's other LAN-only assumptions (`RemoteAdmin`). Reconnects on disconnect with a flat 5 s single-shot timer, no backoff. On a config change it creates a fresh `QMqttClient` and detaches/`deleteLater()`s the old one rather than reusing a single client: with one client, the old connection's asynchronous close was observed tearing down the new connection attempt (tested against two local `mosquitto` brokers).
- **`Mdi`** (`src/mdi.{h,cpp}`) resolves Material Design Icon names as HA sends them (`"mdi:lightbulb-on"`, aliases included) to glyphs in the bundled webfont. It loads the font itself and exposes the registered `fontFamily` (never hardcode it). Unknown names render `help-circle-outline` and warn once. Use it via `qml/MdiIcon.qml` (`icon`, `iconSize`).

### Animated background

`qml/AnimatedBackground.qml` is a diagonal four-color gradient, `span` window diagonals long, drifting back and forth. Drawn plainly, neighboring colors sit only a few 8-bit shades apart across a whole screen, so each shade shows as a flat diagonal stripe (measured: flat color runs averaging ~24px). With Qt Shader Tools in the kit (optional `ShaderTools` component; `qt_add_shaders` compiles `shaders/background.frag` to `:/res/QtHomeAssistant/shaders/background.frag.qsb` and defines `QTHASS_HAS_SHADERS`, exposed as `Controler.backgroundShaderSupported`) the gradient is a `ShaderEffect` that adds triangular noise before quantization, which removes the stripes without visible grain. Without it, or under the software renderer (`GraphicsInfo.api === GraphicsInfo.Software`, which can't run shaders -- note `QT_QPA_PLATFORM=offscreen` on macOS always lands there, so screenshotting the shader path needs a real window), it falls back to the rotated `Rectangle` gradient plus a faint tiled `images/noise.png` overlay, which only hides the stripes since that noise is added after quantization.

### Entity cards

Non-visual code that only needs an entity's live state uses `qml/HassEntity.qml` (`entityId` → `state`, `attributes`, numeric `value`, and `baseValue` converted from kW/kWh to W/Wh). Cards extend `qml/EntityBase.qml`: set `required property string entityId` (cards are configured with `entityId`, like `HassEntity`; `entity_id` only appears as Home Assistant's own payload key) and assign the `update` function property, which EntityBase registers with `HassAPI` in `Component.onCompleted`. See `qml/Light.qml` and `qml/Cards/Weather.qml`.

`qml/Tile.qml` (a Lovelace-style tile card) takes a `features` list of `qml/TileFeature.qml`-derived items (`qml/Features/ToggleFeature.qml`, `qml/Features/LightBrightnessFeature.qml`). That property is declared `list<Item>`, not `list<TileFeature>` -- confirmed on-device that `list<TileFeature>` makes the whole `Tile` type unavailable at runtime on Android (`Type Tile unavailable`, even for a bare `Tile{}` with no `features` set) while working fine on desktop. `list<Item>` keeps the same `features: [A{}, B{}]` declaration syntax and runtime behavior (JS property assignment on each element still goes through its real `TileFeature`-derived type), so don't "fix" it back to `list<TileFeature>`.

Tapping and holding a `Tile` run Lovelace-style actions: `tapAction`, `holdAction`, `iconTapAction`, `iconHoldAction`, each an action name (`"more-info"`, `"toggle"`, `"none"`), an object (`{ action: "more-info", entity: "sensor.other" }`) or a function. Defaults keep the original behavior: a tap opens the details, a tap on the icon toggles (details when the entity can't toggle), a hold does nothing; `iconHoldAction` falls back to `holdAction`. Toggleable domains are automation, fan, humidifier, input_boolean, light, lock, siren, switch, and climate when its `supported_features` has both TURN_ON (128) and TURN_OFF (256) -- so `ToggleFeature` (the details overlay included) shows for those climate entities too. One `TapHandler` (hold threshold 0.5 s, which suppresses `tapped`) serves the whole card and hit-tests the icon itself: a second `TapHandler` on the icon would only grab passively, so both would fire. Feature controls take the press, so tapping or holding them never reaches the tile's actions. Tested on desktop by injecting mouse events from QtTest's `TestCase` helpers in a test dashboard; not yet on Android touch.

### Details overlay

`qml/Details/DetailsOverlay.qml` is the app's one entity details view (Lovelace's more-info), a single instance in `Main.qml` outside the dashboard. Anything, user dashboards included, opens it with `Controler.requestDetails(entityId, name)` (an empty name uses the friendly name); a request while it's open swaps the entity, recreating the content since an `EntityBase` only registers the entity it was created with. It shows the entity as a `Tile` (actions `"none"`, with `ToggleFeature` and `LightBrightnessFeature`, which appear only where supported), when the state last changed, for numeric sensors (`sensor.*` with a unit, a `state_class` or a numeric state) `SensorHistory.qml`, for binary sensors `BinarySensorHistory.qml`, and `DetailsAttributes.qml` (attributes minus internal ones, timestamps in local time). Its content exists only while open; it closes on Escape/Android back (`focus: true` is needed for that), a tap outside, the screensaver starting and a disconnect, and draws a plain background since Material's elevated one doesn't render under the software renderer.

Both history charts extend `HistoryPanel.qml`, which owns the tabs -- the last 24 hours (refetched every 5 minutes) or the 24 hours ending 1, 2, 3 or 7 days ago --, the window, request bookkeeping (`loadRequested(request)` → `done`/`failed`, stale replies dropped) and `history()` (`history/history_during_period`); the subtype's chart is appended below it (Qt Charts, styled with the energy views' `EnergyChartView`/`EnergyValueAxis`). `BinarySensorHistory` is a timeline: an `AreaSeries` over a 0/1 step outline, a bar spanning each period the sensor was on (unavailable counts as off). `SensorHistory` charts the value, its last 24 hours ending in the live value. Sensors with a `state_class` come from 5-minute `recorder/statistics_during_period` (mean line in a min–max band; `total`/`total_increasing` ones have no mean, so each period's last `state`), which stays ~288 points however chatty the sensor -- raw history of a power sensor can be megabytes, the payload size that trips QWebSocket's frame timeout. HA keeps 5-minute statistics for 10 days by default, which covers the 7-day tab. Other sensors, or ones with no statistics yet, use `history/history_during_period` averaged into 5-minute buckets and drawn as steps, since a state holds until it changes. Two ordering traps, both hit while testing: fetch on `offsetDays` changing, not in the `TabBar`'s `onCurrentIndexChanged` (which ran before the binding followed and fetched the previous tab), and `Qt.callLater` the first fetch, because `HassEntity` sets `state` before `attributes`, so `state_class` isn't known yet when the state first arrives.

### Cameras

`examples/office-panel/OfficeCameras.qml` lists `qml/Cameras/CameraCard.qml`s: a `camera_proxy` snapshot reloaded every `refreshSeconds`, opening `CameraStreamPopup.qml` (live view) on tap. Video: Home Assistant's `stream` integration pulls the camera's RTSP(S) stream and remuxes it, without transcoding, into HLS; `camera/stream` returns that HLS URL (token in the path) and QtMultimedia's `Video` plays it through its FFmpeg backend (`libffmpegmediaplugin`, bundled into the APK), which does the decoding. So the app never touches RTSP or encodes anything, but it must be able to decode whatever codec the camera sends (H.264 everywhere; H.265 depends on the device) at that resolution, and HLS adds a few seconds of latency. On weak devices prefer a camera's medium-resolution entity. Along the top of each card (and under the name in the live view) `CameraDetails.qml` shows motion now, dark/light and "last motion ... ago" from `CameraSensors.qml`, which finds the camera's sensors on its device (`config/entity_registry/get` → `search/related`, neither admin-only) by UniFi Protect's names: `binary_sensor.*_motion` (not `*_detections_motion`, a setting), `binary_sensor.*_is_dark`, `event.*_motion_detection` (state = last motion time; without it, when the motion sensor last turned off). `CameraCard`'s `motionEntity`/`darkEntity`/`lastMotionEntity` override the discovery, e.g. for the Reolink, whose device has none of these. Chips for sensors a camera lacks are hidden.

### Alarm

`qml/Alarm/AlarmCard.qml` (`AlarmCard { entityId: "alarm_control_panel...." }`, used on the overview) is a `Tile` subtype showing an alarm panel's state as a tinted shield (blue disarmed, green armed, orange arming/pending, red triggered), so it takes Tile's `tapAction`/`holdAction`/`iconTapAction`/`iconHoldAction`. By default tapping it opens the details overlay, which for `alarm_control_panel` entities shows `AlarmControls.qml` in place of its header tile (and widens itself to 760 px for a keypad, through `DetailsOverlay.preferredWidth`, which `show()` resets for each entity since a destroyed `Binding` doesn't restore its target): the state, Disarm and "Arm <default mode>" (away when supported) buttons, one button per arm mode the entity supports (`supported_features` bits: home 1, away 2, night 4, custom bypass 16, vacation 32; trigger isn't offered), and, when `code_format` is set, a code field -- with a keypad for `"number"` (the field is read-only on Android so the system keyboard doesn't cover it). Arm buttons need a code only when `code_arm_required`; a code is sent with any call when entered, and HA's error (e.g. a wrong code) is shown from the `command` callback's error message. `AlarmEntity.qml` (a `HassEntity`) holds the state-to-label/icon/color mapping, the supported modes and the service calls, shared by the card and the controls.

### Areas

`qml/Area/AreaCard.qml` (`AreaCard { areaId: "living_room"; sensors: [...]; controls: [...] }`) is modeled on Lovelace's [area card](https://www.home-assistant.io/dashboards/area/): a header with the area's name over a line of `AreaSensor.qml`s (icon and state with unit; the icon and binary sensor wording follow HA's device-class defaults; a tap opens the details), then a grid of flat `Tile`s for `controls`. It shows only the entities it's given -- deliberately no discovery of the area's entities, which the user asked for explicitly. A sensor is an entity id or `{entityId, icon}`; a control an entity id or `{entityId, name, icon, iconOnly, tapAction, holdAction}`, where `name` replaces the friendly name, `tapAction` (`"more-info"` by default, or `"toggle"`) applies to the whole tile, icon included, and `iconOnly` controls (a `Tile` with `iconOnly`, no name or state) sit in a row above the other tiles, each group in the order given. `displayType` picks the header: `"picture"` (the area's picture, the default), `"icon"` (the area's icon on an accent tint) or `"url"` (`pictureUrl`, a full URL or a path on the HA server); the icon stands in while a picture loads or when there is none. Name, icon and picture come from `config/area_registry/list`; `/api/image/serve/...` pictures need no auth. The header's rounded top corners are a `MultiEffect` mask, so they're square under the software renderer. `Tile.toggleable` includes climate entities whose `supported_features` has TURN_ON and TURN_OFF (see Entity cards). `examples/area-panel/main.qml` is a single-file dashboard of three area cards, one per `displayType`.

### Weather

`qml/Weather/WeatherCard.qml` (`WeatherCard { entityId: "weather.pirateweather" }`) is modeled on [weather-chart-card](https://github.com/mlamberts78/weather-chart-card): condition icon and name, current temperature with today's high/low, `attributeRows` (entity attributes such as visibility and apparent temperature, skipped when the entity doesn't report them -- met.no's `weather.forecast_home` has neither, PirateWeather has both), and `WeatherForecast.qml`, the daily forecast as columns: day and `WeatherIcon` (condition as layered, colored MDI glyphs), a `Canvas` chart of highs (line with a gradient by temperature) and lows (dotted) over precipitation bars, then precipitation amounts and `WindIndicator` rings (speed in the entity's unit, colored by Beaufort band, notch pointing where the wind blows). Weather entities no longer carry the forecast as an attribute, so it's fetched with `HassAPI.command("call_service", {domain: "weather", service: "get_forecasts", ..., return_response: true})` on creation and every `refreshMinutes` (30); the forecast is under `response[entityId].forecast`. The number of days shown fits the width (56 px per column, at most `maxDays`). `qml/Clock.qml` shows the current condition's `WeatherIcon` next to the time while `showWeather` (default true, off in `Screensaver`/`OfficeDoNotDisturb`) and `weatherEntity` is set (no default); tapping it opens a popup with a `WeatherCard`, created only while open and closed when the screensaver starts. Condition names and number formatting are shared with `WeatherSummary` through `WeatherFormat.js`. `qml/Cards/Weather.qml` is the older icon-only card, unused.

### Do not disturb

Not part of the app shell: `examples/office-panel/OfficeDoNotDisturb.qml` is a `qml/Dashboard/DashboardOverlay.qml` (a full-screen modal `Popup` over everything, the screensaver included, `z: 1`, shown while its `active` is true) that the office dashboard declares, with the clock (`qml/Clock.qml`, shared with the screensaver) and the "do not disturb" gif on black, active whenever its `entityId` -- `input_boolean.bartek_nie_przeszkadac`, set in its `main.qml` -- is on. It exists only while the dashboard does, i.e. while connected. Its button hides it for `snoozeMinutes` (1); the hiding also ends when the entity turns off, so the next do-not-disturb shows it again.

### First-run setup

`qml/Main.qml` shows `qml/Setup/SetupWizard.qml` over everything until `Controler.setupCompleted` (so only on an install with no token yet), and only calls `HassAPI.connect()` (and loads the dashboard) once setup is done; the settings page's "Log in again and set up this device..." clears the flag to run it again. Steps: server address (`ServerStep.qml`; "Skip, keep current connection" when a token is already configured, e.g. bundled), Home Assistant login (`LoginStep.qml`), device options (`OptionsStep.qml`: device name, keep screen awake, screensaver timeout, remote control password/port; applied only on finish).

Login is HA's own HTTP auth API, done natively in `qml/Setup/HassAuth.qml` with `XMLHttpRequest` -- no browser: `GET /auth/providers` (also checks the address is HA), `POST /auth/login_flow` then `/auth/login_flow/<flow_id>` per step (forms are rendered from the step's `data_schema`, so two-factor codes work too), ending in `create_entry` with an authorization code for `POST /auth/token`. `client_id` is `https://github.com/btaczala/qt-hass` with a redirect URI on the same host: HA's IndieAuth check accepts that without fetching anything (verified against the real server), and neither URL is ever opened. On finish the wizard refreshes the access token (it lasts 30 minutes), connects with it, creates a long-lived access token named `Qt Home Assistant: <device name> (<date time>)` over the WebSocket (names must be unique per user), saves that as `Controler.hassToken`, revokes the refresh token and reconnects -- so the app ends up with an ordinary long-lived token, as if pasted in settings. Re-running setup creates a new token and leaves the old one for the user to delete in their HA profile. The flow was tested end to end against a fake HA server (wrong password, 2FA step, token creation, revoke).

### Settings and the dashboard URL

`qml/Settings/SettingsPage.qml` is a full-screen, scrollable settings page with a back button (connection URL/token with "Save and reconnect" / "Use built-in", dashboard URL with Reload, MQTT, theme, navigation bar position, animated background on/off, system tray, idle timeout, About), its content centered and at most 720 px wide. It's a `Popup` in the window overlay rather than an `Item`, because on Android the window's content area stops short of the screen's top and bottom edges (an `Item` filling it left strips of the background showing); `CloseOnEscape` also closes it on Android's back button. It keeps the default z: the screensaver has the same z and, opened later, draws over it, and `DashboardOverlay`s (z 1) are above both. Don't give it a negative z to push it under the screensaver: confirmed on the tablet that a modal popup with z -1 sits under its own modal input blocker, so nothing in it can be tapped. It lives in `Main.qml`, outside the dashboard `Loader`, so settings are reachable before the first successful connection (e.g. to fix a wrong URL): while there's no dashboard, a menu `ToolButton` pinned top-left opens it; once the dashboard is up, that button hides and the navigation bar's Settings button (`Dashboard.menuRequested`) opens it instead.

`Controler.dashboardUrl` (read-only) is where the dashboard comes from, see "User dashboards", and is what `DashboardHost`/`DashboardSync` use. It follows `dashboardSource` (`QSettings` `dashboard/source`, default `url`): `url` is `customDashboardUrl` (`dashboard/url`, default the bundled `DASHBOARD_URL`; saving an empty URL forgets the saved one); `hass` is `dashboardConfig` (`dashboard/config`) in Home Assistant's www folder, `hassDashboardsUrl` + `<config>/main.qml`, where `hassDashboardsUrl` is `http(s)://<host:port of hassUrl>/local/qthass/` (so it follows the connection's URL). HA serves www files but no folder listings (403 for `/local/qthass/`), so the settings page lists the configs from `/local/qthass/index.json`, a JSON array of folder names read by `qml/Settings/HassDashboardList.qml`; it's `examples/index.json`, kept by hand and copied up with the dashboards by `just dashboard-sync` (Homebrew rsync, each `examples/<name>/` to `/config/www/qthass/<name>/`; it refuses an index naming a folder without a `main.qml`). The settings page's Dashboard section edits the source and the config (dropdown, with refresh) or the URL, shows `DashboardHost.statusText` and saves and reloads ("Save and reload", or just "Reload"), then closes the settings to show the result. Settings only QML reads (theme, animated background, `navPosition`, the system tray's `showBattery`/`showNotifications`/`showSettingsAlerts`) live in `qml/Settings/UiSettings.qml`, a `QtCore` `Settings` subtype (category `ui`) that `Main.qml` instantiates once and passes to `SettingsPage`. It's a named type rather than a bare `Settings {}` so qmllint can see its custom properties, and there's a single instance because separate `Settings` instances don't sync live. `Material.theme` is set on the `ApplicationWindow` from it, so don't set a theme on `Dashboard.qml` or individual pages again.

### User dashboards

A dashboard is a directory of QML the user hosts, typically Home Assistant's `/config/www/qthass/` (served without auth at `/local/qthass/`, so nothing secret belongs there), with the dashboard URL pointing at its root file (`.../main.qml`; any name, but not `Dashboard.qml`, whose root would be the directory's own type rather than the module's). Its other files -- the user's own cards -- are listed in a `qmldir` next to it (`MyCard 1.0 MyCard.qml`), which doubles as the download list, since `/local/` can't list a directory; a dashboard with no `qmldir` is a single file. Only QML/JS files are downloaded: pictures need full URLs (or `qrc:` for the app's own, like `images/screensaver.gif`). `examples/office-panel/` is the office panel's real dashboard, and a working example of everything below; it isn't built into the app. User QML runs with the app's full rights (`HassAPI` with the token, `XMLHttpRequest`, ...), so the URL has to be trusted like the app itself. Check a dashboard against the module with `qmllint -I build/debug examples/office-panel/*.qml` (the build dir has `QtHomeAssistant`'s `qmldir` and `.qmltypes`).

`src/dashboardsync.{h,cpp}` (`DashboardSync`, a `QML_SINGLETON`) downloads it: the root file and optional `qmldir` in parallel, then everything the `qmldir` lists (relative paths below the directory only), with the HA token as a Bearer header only when the host and port are Home Assistant's own. A `file://` URL is copied the same way, for writing a dashboard locally. A complete download goes to `AppDataLocation/dashboard/<hash of the files>/`, and `localUrl` points at the root file there. Always a new directory for new content, never an overwrite, because the QML engine caches components by URL: tested on the tablet that loading the same URL again after its files changed gives the old code back, with no request made. Content-named directories also avoid `QQmlEngine::clearComponentCache()`, which is only safe once every object from those components is gone. A failed download changes nothing, so the last good copy stays (`error` says why); the copy is remembered in `QSettings` (`dashboard/cachedUrl`/`cachedDir`/`cachedRoot`/`syncedAt`) and used at startup when it's of the configured URL, then older copies are deleted. `warnings` collects `QQmlEngine::warnings` from the dashboard's files. Logging category `qthass.dashboard`.

`DashboardHost` calls `DashboardSync.sync()` whenever it becomes active (each connect, so at startup and after HA restarts) and on `reload()` (which loads again even when nothing changed). Whenever `localUrl` changes it compiles the root file asynchronously with `Qt.createComponent` (so the error string is available) and a `Loader` creates it. Without a dashboard it shows `qml/Dashboard/DashboardMessage.qml` instead: "No dashboard defined", "Loading the dashboard...", "Couldn't download the dashboard" (no cached copy either) or "The dashboard has errors" (compile errors with cache paths stripped, the root not being a `Dashboard`, or creation failing, with `DashboardSync.warnings`), with Reload and Open settings buttons. It passes `navPosition` to the dashboard and turns its `menuRequested` into opening the settings. Tested on the tablet: download over HTTP, a 404, a broken file then fixed and reloaded, the server going away (last good copy kept, both on reload and at startup).

### Multi-page dashboards (NavBar + StackLayout)

The building blocks live in `qml/Dashboard/`: `Dashboard.qml` is `qml/Navigation/NavBar.qml` over a `StackLayout` whose `currentIndex` is bound to the bar, with a `pages` list of `DashboardPage.qml`s (an `Item` with the `title` and `icon` its NavBar button shows, around content that fills it) that become the `StackLayout`'s children -- declared `list<Item>`, not `list<DashboardPage>`, for the same Android reason as `Tile`'s `features`. Any other child of a `Dashboard` is part of it without being a page (e.g. a `DashboardOverlay`). `screensaverWeatherEntity`/`screensaverEnergyEntities` on the dashboard are what `Main.qml` hands the screensaver (nothing when empty). `navPosition` and `menuRequested` are set/handled by `Main.qml`. The office panel's own dashboard is `examples/office-panel/main.qml` with `OfficeOverview.qml`, `OfficeEnergy.qml`, `OfficeCameras.qml` and `OfficeDoNotDisturb.qml` -- keep house-specific entity ids there, not in the app's cards or shell. Every page is instantiated up front and lives for as long as the dashboard does, so its entities register with `HassAPI` exactly once. An earlier `StackView` version that created a fresh page on each tab switch crashed the QML engine's GC on a real device after a handful of switches, so don't go back to destroying pages on switch. Add a page to a dashboard by adding a file next to its root, listing it in its `qmldir`, and wrapping it in a `DashboardPage` in the root's `pages`.

`NavBar` is modeled on [lovelace-navbar-card](https://github.com/joseluis9595/lovelace-navbar-card): a floating rounded card of icon+label buttons, the current page's icon in an accent-tinted pill, and a Settings button last. `Dashboard.navPosition` docks it centered along the left/right edge (a vertical rail) or the top/bottom edge (a row), and the pages get the rest of the window. `Main.qml` sets it from `UiSettings.navPosition`: `"auto"` (the default) is left when the window is wider than tall, top otherwise, so the pages keep the long side. Bottom is offered but not a default: confirmed on a real device (Fire tablet, Android 9) that Android's immersive-sticky navigation bar lives at the bottom edge and reappears on a touch there even in a fullscreen app, swallowing the first tap into the OS home/back/recents bar instead of the app underneath -- a bottom-docked tab bar was unreliable to tap at all. Its buttons' MDI name property is `iconName`, since `AbstractButton` already has a FINAL `icon` (overriding it makes the type fail to load at runtime, which qmllint doesn't catch).

### Energy overview

`qml/Energy/EnergyFlowPage.qml` (the whole energy page, a built-in; `examples/office-panel/OfficeEnergy.qml` only sets its entities) shows `qml/Energy/EnergyFlowCard.qml`, a power-flow diagram modeled on [power-flow-card-plus](https://github.com/flixlix/power-flow-card-plus): solar on top, grid left, battery right, home at the bottom, with a dot moving along every active route. The card sizes itself to the diagram (`designWidth` × `designHeight` design units) and `EnergyFlowPage.qml` hands it the largest `diagramScale` at which it fits. Individual consumers aren't circles on the diagram -- they're in the home details. A tab bar above it switches the diagram between "Power now" (W) and "Energy today" (Wh since midnight, like energy-flow-card-plus): the route split lives in `EnergyFlows.js`, and in energy mode `HassEnergySource.energyFlows` applies it to each hour of today's 5-minute `change` of the solar, grid and battery (`energy_charged_into_battery`/`energy_discharged_from_battery`) lifetime counters and sums the hours -- not to the day's totals, which would credit night-time grid charging to solar, and not per 5 minutes, since those counters step in 100 Wh. Colors are HA's energy dashboard defaults. The card takes only HA-style readings (`solarPower`, `gridPower` +import/−export, `batteryPower` +discharge/−charge, `batterySoc`, per-device power) and derives the per-route flows itself: export and battery charging are served from solar first. Its diagram is laid out in fixed design units (`designSize`) and scaled to fit. `EnergyFlowLine` advances its dot with a `FrameAnimation` (speed ∝ flow / largest flow, so a speed change doesn't wait for a loop restart), stopped while the page is hidden. The dot follows a separate plain `Path` duplicating the curve, not the `ShapePath` that draws it: `PathInterpolator` on a `ShapePath` never moves (Qt skips the point cache for shape paths, so the position sits at the end point). Tapping any circle (`EnergyNode.clickable`/`clicked`) emits the card's `detailsRequested(node)`; `EnergyFlowPage.qml` opens `qml/Energy/Details/EnergyDetailPopup.qml` (content `Loader`ed only while open, closed when the screensaver starts, since popups draw above it) with `SolarDetail` (tabs, opening on Today: `SolarDay` for today and yesterday -- production vs forecast as a red-orange-green progress bar plus a chart; yesterday has only the forecast's total, since Solcast's `detailedForecast` attribute isn't recorded -- and `SolarWeek`, this locale week's production per day next to its forecast, with Solcast's tomorrow and day-3..7 totals (`solarForecastDayEntities`) for the days ahead), `GridDetail` (today's energy and cost, the best hours ahead to import/export as chips, and hourly prices as a `BarSeries` with those hours shaded), `BatteryDetail` (level, ETA at the current rate, chance of a full charge today, last 7 days of SoC) or `HomeDetail` (consumption now and today, self-sufficiency, where it's coming from, a scrolling list of every consumer sorted by power with its share of home power and energy today -- consumers whose reading is part of another's (`insideOf`) are indented under it and left out of "Rest of home" -- and a chart with lines for the `chartedConsumers` (5) biggest consumers today, created with `createSeries()`). The detail views take plain HA-shaped inputs (`{x, y}` series with x in hours). Their charts are Qt Charts `ChartView`s, styled by `EnergyChartView.qml` (transparent, Material text colors, a "now" marker and `plotX()` placement over an `xMin`..`xMax` range -- plain numbers, since a bar chart's category axis has none -- and `setPoints()` to fill a `LineSeries` from `{x, y}` arrays, touching only changed points) and `EnergyValueAxis.qml`. "Chance of a full charge" is a heuristic, not a model: the rest of today's forecast solar minus `loadProfile`, capped at the battery's max power, is taken as normally distributed with a spread from the same sum over the forecast's 10th/90th percentiles (a 30 % error without them), and the probability is that it covers the energy missing to 100 %. The page is fed by `qml/Energy/HassEnergySource.qml`, which outputs everything in those units from Home Assistant. Every entity id it reads (and the battery's max power) is a `required` property on it and on `EnergyFlowPage`, set in `OfficeEnergy.qml` -- the one place to change which entities the page uses; `HassEnergySource` documents what each must provide. Live flows, battery SoC/capacity/low-SoC limit and today's solar energy come from the SELFA inverter (`sensor.selfa_inverter_*`; `grid_meter_power_inverted` is the import-positive one -- checked against home − solar − battery, `grid_meter_power` is the opposite sign), home consumers from `consumerEntities` -- the HA Energy dashboard's individual devices (`energy/get_prefs` → `device_consumption`, whose `included_in_stat` became `insideOf`), except that the car uses `sensor.evcc_garage_charge_power` like the Lovelace power-flow cards rather than the Wallbox sensor --, the forecast from Solcast's `detailedForecast` attribute on `sensor.solcast_pv_forecast_prognoza_na_dzisiaj` (30-minute average kW, plotted at period midpoints, plus `pv_estimate10`/`pv_estimate90`), and prices from the `All prices` attribute of Pstryk's `sensor.pstryk_current_buy_price`/`current_sell_price` (the other Pstryk integration's `pstryk_buy_current_price` disagrees with it and with evcc). History comes from recorder statistics through `HassAPI.command`: 5-minute solar, home and consumer power means and grid import/export `change` since midnight (requested with `units` so HA converts to W/Wh) (cost = each 5-minute step × that hour's price), and hourly SoC means plus hourly home energy `change` over the last week (averaged per hour of day into the load profile); for the solar tabs, yesterday's 5-minute solar means, hourly `change` of the lifetime `sensor.selfa_inverter_total_pv_generation` per day (not the daily sensor, whose `change` goes negative across its midnight reset) and past days' forecasts as the Solcast today sensor's last state each day (`history/history_during_period`). Battery max power isn't exposed, so it's a 5 kW constant (the inverter's battery power scheduling limit). Today's series use hours since local midnight, the SoC week local hours since the epoch.

### MDI table generation

`tools/generate_mdi_table.py` runs at **configure time** (`execute_process`) and writes `build/*/generated/mdi_icons_data.h`, a sorted name→codepoint table. It is generated, never committed. It cross-checks every codepoint against the font's cmap and fails configure on mismatch. Its inputs `fonts/materialdesignicons-webfont.ttf` and `fonts/materialdesignicons-meta.json` are vendored. To upgrade MDI (the only networked step): `python3 tools/generate_mdi_table.py --fetch <version>`. Currently 7.4.47.

### CMake gotchas (already handled, don't undo)

- `qtquickcontrols2.conf` is added with a separate `qt_add_resources(... PREFIX "/")`. Qt only reads it from `:/qtquickcontrols2.conf`, and inside the QML module's resources the Material style silently doesn't apply.
- `src/` is on the include path because the generated QML type registration includes headers by basename.
- All Android-only CMake lives in `cmake/android.cmake`, pulled in from the root `CMakeLists.txt` by a single `if(ANDROID) include(cmake/android.cmake) endif()` after the target is defined; keep new Android settings there rather than in the root file.
- Android builds set `QT_ANDROID_EXTRA_LIBS` to `android/openssl/arm64-v8a/{libcrypto_3,libssl_3}.so`, vendored (Apache-2.0) from [KDAB/android_openssl](https://github.com/KDAB/android_openssl) `no-asm` build (commit `b71f1470`). Android doesn't expose OpenSSL to NDK apps, so without this `QtWebSockets` has no TLS backend and `wss://` connections fail at the handshake with "No functional TLS backend was found". Only arm64-v8a is vendored; another ABI or a Release Android build needs its own lib pair added under `android/openssl/<abi>` (see the upstream repo's `ssl_3/<abi>` for the non-`no-asm` variant).
